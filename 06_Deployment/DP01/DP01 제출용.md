# 모델 배포 개론 Day 1 — 체크포인트 답변

**주제: RESTful API & 모델 직렬화**

## ✅ 1절 체크포인트 (들어가며)

**1. `.pth` 파일만 전달했을 때, 상대방이 모델을 바로 사용할 수 없는 이유는 무엇입니까?**
.pth 파일에는 가중치(숫자)만 들어있고, 모델의 구조(설계도, 즉 클래스 정의)는 저장되지 않기 때문이다.

**2. 모델 학습(Training)과 모델 배포(Serving)의 핵심 차이를 한 문장으로 설명할 수 있습니까?**
학습은 데이터로 가중치를 찾아 모델을 똑똑하게 만드는 단계이고, 배포는 완성된 모델을 다른 환경·사람·언어가 안정적으로 쓸 수 있게 꺼내놓는 단계이다.

**3. 모델 배포에서 사용자와 서버가 소통하는 방식은 무엇입니까?**
REST API를 통해, 약속된 형식(주로 JSON)으로 HTTP 요청/응답을 주고받는다. 사용자는 모델 내부를 몰라도 규약(주문서)만 지키면 된다.

## ✅ 2절 체크포인트 (환경 세팅)

**1. 가상환경 없이 `pip install`을 하면 패키지가 어디에 설치됩니까? 그것이 왜 문제가 될 수 있습니까?**
시스템 전역 Python(내 컴퓨터 전체가 공유하는 공간)에 설치된다. 여러 프로젝트가 그 한 공간을 같이 쓰기 때문에, A 프로젝트는 torch 2.1이 필요한데 B는 torch 2.3이 필요하면 서로 덮어쓰며 충돌하고, 무엇이 어느 프로젝트 것인지 알 수 없어 환경 재현이 어려워진다.

**2. `pip freeze`로 생성한 파일과 직접 작성한 `requirements.txt`의 차이는 무엇입니까?**
pip freeze는 현재 환경의 모든 패키지를 하위 의존성까지 정확한 버전으로 박제한다. 완벽한 재현엔 좋지만 목록이 길고 불필요한 것도 섞인다. 직접 작성은 핵심 패키지만 골라 적어 읽기 쉽고 관리가 편하지만, 하위 의존성 버전은 유동적이다.

**3. 동료에게 프로젝트를 전달할 때, `.venv` 폴더 대신 무엇을 공유해야 합니까?**
requirements.txt(와 소스 코드)를 공유한다. .venv 폴더는 무겁고 내 컴퓨터 경로·OS에 종속되어 있어서, 복사해줘도 남의 컴퓨터에선 동작하지 않는다. 대신 준비물 목록(requirements.txt)만 주면, 받는 사람이 자기 환경에서 `pip install -r requirements.txt`로 똑같이 재현할 수 있다.

## ✅ 3절 체크포인트 (RESTful API)

**1. 모델 추론 요청에 GET이 아닌 POST를 사용하는 이유는 무엇입니까?**
추론은 입력 데이터(사진·문장 등)를 서버에 보내서 처리를 요청하는 작업이다. GET은 본문(body)이 없는 조회 전용이라 데이터를 실어 보낼 수 없지만, POST는 입력을 본문에 담아 보낼 수 있으므로 추론에는 POST를 사용한다.

**2. 상태 코드 `422`는 어떤 상황에서 발생합니까?**
입력 검증 실패일 때 발생한다. 요청은 서버에 잘 도착했고 JSON도 읽혔지만, 데이터의 형식이나 값이 서버가 정한 규약과 맞지 않을 때 발생한다.

**3. `requests.post(url, json=data)`에서 `json=` 파라미터는 내부적으로 어떤 일을 합니까?**
① Python 딕셔너리(data)를 JSON 문자열로 자동 변환(직렬화)하고, ② 요청 헤더에 `Content-Type: application/json`을 자동으로 붙인다("지금 JSON을 보낸다"고 알려주는 표시).

**4. Python의 `True`는 JSON에서 어떻게 표현됩니까?**
`true`로 표현된다. (함께 외워두면 좋은 것: `False → false`, `None → null`, 그리고 문자열은 반드시 "큰따옴표".)

## ✅ 4절 체크포인트 (모델 직렬화)

**1. `state_dict`로 저장한 `.pth` 파일을 불러올 때, 모델 클래스 정의가 필요한 이유는 무엇입니까?**
.pth에는 가중치(숫자)만 있고 모델 구조(설계도)는 없기 때문이다. 그래서 똑같은 클래스로 빈 모델을 먼저 만들어 놓고, 그 자리에 .pth의 숫자를 채워 넣어야 한다. 설계도 없이 숫자만으로는 모델을 복원할 수 없다.

**2. `torch.jit.trace`와 `torch.jit.script`는 각각 어떤 상황에서 사용합니까?**
trace는 더미 입력을 한 번 흘려보내 실행 경로를 기록하며, 분기(if/else)가 없는 대부분의 모델에 적합하고 안정적이다(단, 입력에 따라 경로가 달라지는 부분은 기록하지 못한다). script는 코드를 분석·컴파일하여 if/else·반복문 같은 동적 제어 흐름도 변환할 수 있다. 기본은 trace이며, 입력에 따라 경로가 바뀌면 script를 사용한다.

**3. ONNX의 가장 큰 장점은 무엇이며, 어떤 상황에서 선택해야 합니까?**
가장 큰 장점은 프레임워크 독립성이다 — PyTorch·TensorFlow 등 어디서 만들든 변환되고, ONNX Runtime·TensorRT 등에서 여러 언어로 빠르게 실행된다. 추론 속도가 중요한 프로덕션이거나 다른 언어·최적화 엔진에서 실행해야 할 때 선택한다.

**4. `torch.onnx.export()`에서 `dynamic_axes`를 지정하지 않으면 어떤 문제가 생길 수 있습니까?**
내보낼 때 사용한 더미 입력의 배치 크기(보통 1)로 고정된다. 그러면 배포 후 여러 개를 한 번에 처리하는 배치 추론이 불가능하거나 에러가 난다. dynamic_axes로 배치 축을 '가변'으로 열어줘야 여러 입력을 한꺼번에 넣을 수 있다.

## ✅ 마치며 — 종합 점검 (Q1 ~ Q10)

### [섹션 1: 들어가며]

**Q1. 모델 학습과 모델 배포의 핵심 차이를 한 문장으로 설명하세요.**
학습(Training)은 데이터를 이용해 모델의 가중치를 찾아 모델을 똑똑하게 만드는 단계이며, 배포(Serving)는 완성된 모델을 다른 환경·사용자·언어가 안정적으로 사용할 수 있도록 제공하는 단계이다.

**Q2. "내 컴퓨터에서는 되는데" 문제의 근본 원인은 무엇입니까?**
모델이 특정 실행 환경(패키지 버전, 운영체제, 경로 등)에 의존하고 있으며, 그 환경이 다른 사람에게 동일하게 공유·재현되지 않기 때문이다.

### [섹션 2: 환경 세팅]

**Q3. 가상환경을 사용하지 않으면 어떤 문제가 발생할 수 있습니까?**
패키지가 시스템 전역 Python 공간에 설치되어, 프로젝트마다 요구하는 버전이 다를 경우 버전 충돌이 발생하고 환경이 오염된다. 그 결과 다른 환경에서 동일하게 재현하기 어려워진다.

**Q4. pip freeze와 직접 작성한 requirements.txt의 용도 차이는?**
pip freeze는 현재 환경의 모든 패키지를 하위 의존성까지 정확한 버전으로 기록하여 정밀한 재현에 적합하다. 직접 작성한 requirements.txt는 핵심 패키지만 명시하여 가독성과 관리 편의성에 적합하다.

### [섹션 3: RESTful API]

**Q5. 모델 추론 요청에 POST를 사용하는 이유는?**
추론은 입력 데이터를 서버로 전송하여 처리를 요청하는 작업이다. GET은 본문(body)이 없는 조회 전용 메서드인 반면, POST는 입력 데이터를 본문에 담아 전송할 수 있으므로 추론 요청에 적합하다.

**Q6. 상태 코드 200, 400, 500은 각각 어떤 상황을 의미합니까?**
200은 요청이 정상적으로 처리된 성공 상태를, 400은 요청 자체가 잘못된 클라이언트 측 오류를, 500은 서버 내부에서 발생한 서버 측 오류를 의미한다.

### [섹션 4: 모델 직렬화]

**Q7. state_dict 방식은 왜 모델 클래스 정의가 필요합니까?**
state_dict로 저장한 .pth 파일에는 가중치(수치)만 저장되고 모델의 구조는 포함되지 않기 때문이다. 따라서 불러올 때는 동일한 클래스 정의로 빈 모델을 먼저 생성한 뒤, load_state_dict()를 통해 가중치를 채워야 한다.

**Q8. ONNX의 가장 큰 장점과, 사용해야 할 시점은?**
가장 큰 장점은 프레임워크 독립성으로, 어떤 프레임워크에서 만든 모델이든 변환할 수 있고 ONNX Runtime, TensorRT, OpenVINO 등에서 다양한 언어로 빠르게 실행할 수 있다. 추론 속도가 중요한 프로덕션 환경이거나, 다른 프레임워크·언어·최적화 엔진에서 모델을 실행해야 할 때 선택한다.

### [섹션 5: 실습]

**Q9. 모델 저장 전에 model.eval()을 호출해야 하는 이유는?**
Dropout, BatchNorm 등의 계층은 학습 모드와 추론 모드에서 동작이 다르기 때문이다. 저장 전에 model.eval()을 호출하여 추론 모드로 고정해야 배포 후에도 일관되고 올바른 추론 결과를 얻을 수 있다.

**Q10. predict() 함수를 별도 모듈로 분리한 이유는 무엇입니까?**
추론 로직(전처리 → 추론 → 후처리)을 재사용하고 테스트하기 쉽게 만들며, API 코드와 모델 로직을 분리(관심사 분리)하기 위함이다. 이를 통해 서버는 해당 함수만 호출하면 되므로 코드의 유지보수성이 향상된다.
